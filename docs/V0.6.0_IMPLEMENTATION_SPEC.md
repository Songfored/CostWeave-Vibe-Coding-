# CostWeave v0.6.0 Decision Intelligence Lab 精确实施规格

版本：Revision 1  
基线：v0.5.8.4  
目标：v0.6.0  
适用执行者：低能力模型或需要逐步审查的开发者

## 0. 版本目标

### 0.1 唯一目标

建立一个离线、确定性、可审计的 Decision Intelligence Lab。后续任何 Planner、Router、MetaController 和学习算法，都必须通过同一组合同：

- Task/System Belief；
- Capability Posterior；
- Whole Strategy；
- Decision Trace；
- Outcome Credit；
- Dataset Manifest；
- Tournament。

### 0.2 本版明确不做

- 不训练 Router；
- 不连接真实 Provider；
- 不开启网络；
- 不调用本地或云模型；
- 不实现真实 EVC、Probe 或 MultiPlanner 调用；
- 不实现 LiteLLM、LangGraph、TensorZero Adapter；
- 不执行自动 Policy Promotion；
- 不引入新的运行依赖；
- 不宣称降本、提速、超过 Claude 或超过竞品。

内置 Seed 一律标记 E0-simulated。公共历史输出矩阵最多标记 E1-public-replay，不能冒充当前 Provider 调用。

## 3. 全部合同的共同规则

所有合同必须：

- 使用 dataclass(frozen=True, slots=True)；
- 在 __post_init__ 中验证；
- 提供 to_dict；
- 需要外部导入的合同提供 from_dict；
- from_dict 拒绝未知字段；
- 输出只含有限 JSON 值；
- Map 序列化前按 Key 排序；
- Set 不进入公开合同；
- ID 使用 SHA-256 前 32 位；
- 时间不参与内容 ID；
- 不使用 datetime.now 作为函数默认值；
- 相同内容生成相同 ID；
- Bool 不得当成 Int 或 Float。

### 12.1 Utility

每 Case：

~~~text
quality_weight * quality_score
- cost_weight * cost_usd
- latency_weight * (latency_ms / 1000)
~~~

Latency 缺失时：

- latency_weight > 0：Tournament 失败；
- latency_weight == 0：允许，但报告 latency_available=false；
- 绝不能把缺失 Latency 当 0。

## 15. Claim Gate

文件：costweave/benchmarks/claims.py

固定门：

~~~python
QUALITY_NON_INFERIORITY_PP = -2.0
MINIMUM_COST_REDUCTION_PCT = 10.0
MINIMUM_QUALITY_IMPROVEMENT_PP = 3.0
MAXIMUM_P95_LATENCY_REGRESSION_PCT = 10.0
~~~

胜出需要满足以下之一：

1. Quality Difference 的 95% Lower >= -2pp，Cost Reduction 95% Lower >= 10%，P95 Regression <= 10%；
2. Cost 不显著更差，Quality Improvement 95% Lower >= 3pp，P95 Regression <= 10%。

- Case Count >= minimum_claim_cases；
- Evidence 至少 E1；
- Test Partition；
- 无泄漏；
- Cost 完整；
- 比较 Latency 时 Latency 完整；
- Candidate 不是 Oracle；
- Candidate 与 Baseline 不同；
- Blind Fields 未暴露。

Seed 只有 12 个 Case，因此 Claim 必须是 insufficient_sample。

## 20. Tournament Runner

~~~python
class TournamentRunner:
    def run(
        self,
        *,
        spec: TournamentSpecV1,
        manifest: DatasetManifestV1,
        records: Sequence[RoutingRecordV1],
        policies: Sequence[TournamentPolicy],
    ) -> TournamentReportV1: ...
~~~

执行顺序固定：

1. 验证 Manifest 与 Records Hash；
2. 只取 Spec Partition；
3. 确认 Strong/Cheap 每 Case 可用；

5. 构造 Blind Case View；
6. 调用 Policy；
7. 验证 Decision Case/Policy/Model；
8. 解析选中 Record；
9. 计算 Case Outcome/Utility；
10. 计算 Oracle 诊断；
11. 聚合 Metrics；
12. 与 Baseline 做 Paired Bootstrap；
13. 运行 Claim Gate；
14. 生成 Deterministic Report Hash；
15. 返回报告，不自动写 Store。

整个 Tournament 必须失败的情况：

- Manifest Hash 不匹配；
- Blind Field 暴露；
- Policy 选择不存在的 Model；
- Decision Case/Policy 不匹配；
- Baseline 全部 Abstain；
- Utility 必需字段缺失；
- Bootstrap 失败；
- 出现非有限 Metrics。

Policy 合法 Abstain 不让 Tournament 失败，但降低 Coverage。

Report 必须包含：

- Spec 和 Manifest；
- Policy Metrics；
- Oracle Diagnostics；
- Candidate-vs-Baseline；
- Bootstrap；
- Claim Gate；
- Leakage Checks；
- Evidence Level；
- Network Calls=0；
- Provider Calls=0；
- Generated At；
- Report Hash。

## 27. 最常见的错误

1. Missing Latency 填 0；正确值是 None，需要 Latency 时失败。
2. Policy 看见 Quality/Accepted；正确做法是 Blind Case View。
3. 用 Test Outcome 选择每 Case 最佳模型；那是 Oracle 泄漏。
4. 12 个 Seed Case 宣称胜出；正确结果是样本不足。
5. 使用内置 hash；正确使用 SHA-256。
6. Timestamp 进入 Content ID；正确排除。
7. 相同 ID 不同内容时覆盖；正确抛冲突。
8. E0 Seed Credit 标为可学习；正确为 False。
9. 修改 Migration 029；正确新增 030。
10. Tournament 写进 Server；正确放 Runner/Service。
11. 创建第二个 Runtime DB；正确复用 ControlKernel Path。
12. 修改历史组件 Schema；正确只更新当前 Runtime 门。
13. 所有文件写完才测试；正确每个工作包单独测试。
14. Claim=False 导致 CLI 失败；正确区分“未胜出”和“执行错误”。
15. 因测试通过就写“更智能”；正确只声明实验室合同已建立。
