## 1. 版本结论

v0.5 不应只是增加更多 Agent，也不应把某一家厂商内部的模型分工规则硬编码到产品中。

v0.5 的目标是把 CostWeave 从“基于先验和规则的多模型编排器”升级成：

> 一个能够先判断是否值得规划、是否值得多模型共同规划，再在跨厂商、本地与云端候选中，以验收成功率、全链路成本、完成时间、风险和实时容量为共同目标进行决策，并从可验证结果中持续校准的控制平面。

它必须解决以下问题：

1. 不局限于 GPT 或任何单一厂商。
2. 简单任务允许 `NO_DELEGATION`，避免为了多 Agent 而多 Agent。
3. 自动选择直接执行、SinglePlanner、MultiPlanner、直接高级模型或人工确认。
4. 管理深度固定为两层，禁止无限递归增加 Planner。
5. MultiPlanner 必须通过收益门控，不能用多次昂贵调用替代判断。
6. 低价模型只有在“完成一个验收合格结果”的期望总成本更低时才被选择。
7. 本地资源预计无法满足并发或期限时，必须在执行前分流。
8. 模型之间使用结构化、版本化合同交接，不能只转发聊天记录。
9. 执行中根据证据更新成功概率，优先局部修复，只有根计划失效时才全局重规划。
10. 成功和失败数据必须能够归因、回放、校准和回滚，不能直接污染生产策略。

## 2. 与 v0.4 的边界

v0.5 不是对 v0.4 未完成部分的改名。

v0.4 提供可靠地“执行一次决策”所需的基础：

- 版本化合同、状态机和 EventStore
- Artifact 血缘与可恢复 DAG
- 并行执行、准入、租约、取消和幂等
- 全链路成本账本和资源组合优化
- 证据验收、局部恢复和结果预测
- Outcome 数据、媒体工作流与产品加固

v0.5 在这些基础上回答更高一层的问题：

- 这次任务是否需要独立 Planner？
- 一个 Planner 是否足够？
- 多个 Planner 带来的预期收益是否超过管理成本？
- 应选哪些不同厂商、不同部署和不同视角的 Planner？
- 哪条执行路径在当前负载下具有最低预期总损失？
- 历史数据能否证明新策略比 v0.4、人工静态路由和全强模型基线更好？

当前代码已完成到 v0.4.9，合同、持久化控制内核、Artifact Graph、资源/成本租约、Placement、证据验收、分级恢复、多结局预测、Outcome 归因、分层后验、受控媒体工作流、备份恢复与发布加固已成为可靠基线。因此 v0.5 可以在这一冻结基线上继续实现跨厂商 MultiPlanner 与 MetaPlanner。

## 4. 两层 Planner：合理，但必须是封闭结构

### 4.1 第一层不是“更高级的 Planner”

建议产品内部将 MetaPlanner 命名为 `PlanningGovernor`，中文为“规划治理器”。

它不生成完整方案，不拆解执行节点，也不能再创建另一个 MetaPlanner。它只负责：

1. 提取任务难度、风险、歧义和资源特征。
2. 判断是否需要独立规划。
3. 在 SinglePlanner 与 MultiPlanner 之间选择。
4. 分配规划成本、时间、人数和模型多样性预算。
5. 在自身判断不可靠时直接升级高级模型或请求用户补充关键约束。

第二层才是真正产生计划的 Planner 层。MultiPlanner 内部的裁决器属于同一规划阶段，不构成第三层管理。

### 4.2 硬性递归限制

```json
{
  "max_management_depth": 2,
  "governor_can_spawn_governor": false,
  "planner_can_spawn_planner": false,
  "max_planners_per_round": 3,
  "max_adjudication_rounds": 1,
  "max_full_replans": 1,
  "max_node_escalations": 2
}
```

管理深度、规划调用数和重规划次数必须由确定性控制内核执行，不能只写在提示词里。

### 4.3 PlanningDecision

## 5. 不用单一“难度分数”

任务难度必须表示为向量和置信区间：

```text
TaskDifficultyVector =
  需求歧义
  + 分解不确定性
  + 新颖性
  + 领域专业性
  + 跨领域耦合
  + 上下文与多模态负担
  + 工具链深度
  + 验证难度
  + 错误损失
  + 不可逆性
  + 并发与期限压力
```

同一个“修改 CSS”可能是局部颜色修改，也可能涉及 Canvas、响应式布局和 WebGL；同一个“扫描代码”也可能是普通符号查找或安全审计。路由不能只依赖任务名称和关键词。

模型能力也按同一维度维护，并精确到：

```text
模型版本 × 部署端点 × 推理配置 × 任务族 × 工具配置
```

适配不是让能力分数机械地等于难度分数，而是：

1. 先过滤上下文、模态、工具、隐私、权限、地域、预算和期限等硬约束。
2. 使用历史后验预测成功率、成本和时延分布。
3. 对样本不足和资料过期加入不确定性惩罚。
4. 根据风险保留安全余量：低风险可较小，高风险必须更保守。
5. 若所有低价模型的成功率保守下界都不足，直接选择高级模型，不先便宜试错。

## 6. Planner 与 MultiPlanner 的量化选择

### 6.1 优化目标

对每条可行路线计算：

```text
ExpectedTotalLoss(route)
  = λc × E[全链路成本]
  + λt × E[端到端时间]
  + λq × (1 - Psuccess)
  + λr × ExpectedErrorLoss
  + λh × CoordinationOverhead
```

全链路成本必须包含：

- Planning 与 MetaPlanning
- 输入、输出和重复上下文搬运
- Executor、工具与 Validator
- 缓存未命中
- 失败重试、模型升级和返工
- 本地 GPU、内存、能耗、折旧与排队时间
- 延迟造成的业务损失

系统选择满足所有硬约束且 `ExpectedTotalLoss` 最低的路线，而不是简单选择 token 单价最低的模型。

### 6.2 Value of Deliberation

```text
VoD
  = ExpectedLoss(SinglePlanner)
  - ExpectedLoss(MultiPlanner)
```

只有当 `VoD` 大于安全边际，并且规划预算没有超过上限时，才能启用 MultiPlanner。

MultiPlanner 的候选触发信号包括：

- 高风险或不可逆任务
- 初始 `Psuccess < 0.75`
- 难度估计区间宽度大于 `0.25`
- 两个独立轻量判定器分歧大于 `0.30`
- 多领域强耦合
- 需求存在多种合理解释
- 同类任务历史规划失败率较高

这些只是候选条件，不是无条件触发器；最终仍须满足 `VoD > 0`。

### 6.3 规划开销上限

- 普通任务：规划总成本不超过任务总预算的 15%
- 高风险任务：经策略批准可提高到 25%
- 边界明确且可由确定性工具完成的任务：优先 `NO_DELEGATION`
- 规划预计比执行本身更贵时：禁止 MultiPlanner

## 7. MultiPlanner 协议

MultiPlanner 不是多个模型长时间自由讨论，也不是简单多数投票。

固定流程：

1. 选择 2～3 个具有互补视角的 Planner。
2. 独立、并行生成提案，彼此不可见，降低锚定和从众。
3. 所有提案使用同一 `PlanProposal` Schema。
4. 提案匿名化，避免厂商和模型品牌偏见。
5. 先进行确定性约束检查，再做一次受限的证据裁决。
6. 选择单一方案，或合并可证明互补且无冲突的部分。
7. 核心假设仍冲突时，升级高级裁决模型或用户，不继续增加管理层。

推荐的异质角色：

- `DomainPlanner`：目标、技术方案与领域约束
- `EconomicsPlanner`：成本、并行度、关键路径与资源组合
- `RiskPlanner`：失败模式、验收、权限、回滚与不可逆风险

异质性应优先考虑不同训练家族、Provider、部署方式和提示视角。三个高度相似的模型重复回答，通常只是更昂贵的相关错误。

## 8. 跨厂商角色与模型目录

核心代码只认识能力、角色、约束和适配器，不认识 Sol、Terra、Luna 或任何固定品牌。

### 8.1 RoleSpec 与 ModelProfile 分离

`RoleSpec` 表示系统需要什么：

```json

  "role_id": "risk_planner",
  "required_capabilities": {},
  "required_tools": [],
  "minimum_success_probability": 0.0,
  "permission_profile": "read_only",
  "independence_requirements": [],
  "escalation_policy": "policy-id"
}
```

`ModelProfile` 表示当前模型实际能提供什么：

```json
{
  "model_id": "provider:model:version",
  "provider": "provider-name",
  "deployment": "cloud|local",
  "capabilities": {},
  "modalities": [],
  "tools": [],
  "context_window": 0,
  "pricing": {
    "input_per_million": 0.0,
    "output_per_million": 0.0,
    "currency": "USD",
    "effective_at": "2026-07-19"
  },
  "latency": {"p50_ms": 0, "p95_ms": 0},
  "limits": {
    "max_concurrency": 0,
    "requests_per_minute": 0
  },
  "data_policy": {
    "regions": [],
    "allows_sensitive_data": false
  },
  "empirical_posterior": {
    "sample_size": 0,
    "success_rate": null,
    "confidence_interval": null
  },
  "source": "manual|import|measured",
  "profile_version": 1
}
```

推理强度与权限等级必须分离。更强的推理配置不自动获得数据库、安全、认证、生产环境或不可逆操作权限。

### 8.2 数据维护

模型信息继续支持编辑和 JSON/CSV 导入导出，并新增：

- 价格、汇率、计费单位和生效时间版本化
- 数据来源、核验时间和可信度
- 本地硬件成本、吞吐、显存、能耗与队列画像
- Provider 配额、限流、地域和数据政策
- 厂商先验与 CostWeave 实测后验分离
- 历史版本保留，保证旧路由可重放

资料过期或可信度不足时只能降权或退出自动路由，不能静默当作最新事实。

### 8.3 适配器范围

v0.5.1 不要求真实付费 API。v0.5 必须先提供：

- Provider-neutral Adapter 接口
- `MockProvider` 与可重复的失败、延迟、限流模拟
- OpenAI-compatible HTTP Adapter
- 本地 HTTP Adapter，用于兼容常见本地推理服务
- 插件式自定义 Adapter

默认配置不得产生付费调用。真实 Provider 连接通过 Feature Flag 和用户密钥显式启用。

## 10. 本地模型与实时容量

本地模型适合作为常规特征提取器和低风险调度助手，但不应成为无条件的最高决策者。

建议采用混合控制平面：

- 确定性规则：权限、隐私、预算、并发、地域和不可逆边界
- 本地轻量模型：任务特征、常规模式和候选排序
- 高级模型：高歧义、高影响、低置信度和重大冲突
- 人工：缺少授权、不可逆高风险或价值判断无法自动确定

本地资源准入预测：

```text
PredictedLocalLatency
  = QueueWait
  + ServiceTime
  + ValidationTime
  + RetryRisk
```

资源负载：

```text
ρ = 预测到达率 / (并发槽 × 服务率)
```

初始策略：

- `ρ > 0.70`：黄灯，开始预分流
- `ρ > 0.85` 或 deadline miss 概率大于 20%：新任务转云端或受控排队
- `ρ > 0.95`：只接高优先级任务并启用 Admission Control

如果本地路线的预计总损失高于云端，就不应因为“本地 token 免费”而坚持本地。

## 11. 并行、检查与恢复

v0.5 复用 v0.4 的 Artifact DAG 和并行运行时，并增加由 PlanningGovernor 产生的规划预算与并行策略。

并行收益必须计算：

```text
ParallelBenefit
  = CriticalPathReduction
  - DuplicatedContextCost
  - CoordinationCost
  - ResourceContentionLoss
```

只有正收益的独立节点才并行。系统需要：

- Provider 和本地设备独立 Bulkhead
- 限流、熔断、退避和备用路线
- 幂等键，防止超时后的重复执行和重复计费
- 非阻塞审批，只暂停受影响子图
- 分支隔离，未验收结果不能进入主状态
- 一个分支已满足目标时取消不再需要的推测分支

### 11.1 检查点

不检查每一句响应。检查发生在：

- 规划完成后
- DAG 节点交付时
- 高风险或不可逆操作前
- 关键里程碑
- 最终合并前

证据优先级：

```text
确定性测试、Schema、编译和规则
  > 专用验证器或工具
  > 与生成模型独立的 Judge
  > 用户或人工判断
```

模型自报置信度只能作为经过历史校准的弱特征，不能单独决定成功。

### 11.2 实时更新与恢复

检查点使用测试通过率、约束覆盖、证据完整度、模型冲突、预算消耗率、依赖阻塞和剩余关键路径更新 `Pcomplete`。

初始阈值：

- 低风险：`Pcomplete < 0.60` 进入恢复判断
- 中风险：`Pcomplete < 0.75`
- 高风险：`Pcomplete < 0.90`

恢复顺序：

```text
修复当前节点
→ 更换更适配模型重做当前节点
→ 重规划受影响子图
→ 根假设或任务树失效时进行一次全局重规划
→ 高级模型或人工
```

全局重规划不删除全部成果。已验收且未被污染的 Artifact 必须保留。

## 12. 受控自我学习

v0.5 的“自我学习”首先是调度系统学习，不是让基础模型在线自由训练，也不是让生产系统根据最近几次结果自动改写提示词。

### 12.1 OutcomeRecord

至少记录：

- 匿名化任务特征与 Task Contract
- 规划模式和 Planner panel
- 所有可行候选及淘汰原因
- 每条路线预测的成功率、成本和时延
- 最终选择及选择概率 propensity
- 模型、端点、提示词、目录、策略和验收规则版本
- 实际 token、费用、时延、队列和工具成本
- 检查点、验证证据、升级、重试和重规划原因
- 用户接受、用户改写和延迟反馈
- 失败分类和根因

未经独立验收的模型输出不能作为成功标签。

### 12.2 三层更新

1. 快速更新端点健康、队列、吞吐和故障率。
2. 周期性更新任务族成功率、成本、时延和概率校准器。
3. 路由策略只有经过离线回放、Shadow 和 Canary 后才能发布。

所有策略版本必须可解释、可重放、可一键回滚。

### 12.3 防污染和漂移

- 按时间和项目划分训练、校准与测试集
- 去重，避免同一任务同时进入训练和测试
- 标签携带来源、证据等级和置信度
- 敏感原文默认不进入学习库
- 支持脱敏、TTL 和删除
- 高风险任务线上探索率为 0

冻结学习的初始信号：

- `PSI > 0.20`
- `ECE` 恶化超过 `0.03`
- 某任务族成功率下降超过 5 个百分点
- 成本或时延 p95 连续三个窗口恶化超过 20%

## 13. 成败衡量

### 13.1 三个主 KPI

#### KPI 1：Cost per Accepted Task

```text
CPS
  = 规划 + 执行 + 验证 + 工具 + 上下文搬运
  + 本地算力 + 重试 + 升级 + 返工
  ──────────────────────────────────
              最终验收成功数
```

这是 v0.5 的主成本指标。单次 token 成本下降不代表系统更省。

#### KPI 2：Verified Success Rate

Success 必须在执行前通过 Success Contract 预注册。所有硬验收条件通过才算成功，软评分不能覆盖硬失败。

#### KPI 3：Time to Accepted Result

从任务进入到最终可验收结果的端到端时间，同时报告 p50 和 p95。

### 13.2 诊断指标

- First-pass Success Rate
- Retry、Escalation、Subgraph Replan 和 Full Replan Rate
- Planning Cost Ratio
- Wasted Token / Duplicate Work Ratio
- Handoff Defect Rate
- Budget、Permission 和 SLA Violation
- Probability Calibration：ECE 与 Brier Score
- Local Admission Accuracy
- Parallel Critical-path Reduction
- 用户改写率与人工干预率

### 13.3 Routing Regret

```text
Regret
  = ActualRouteLoss
  - BestFeasibleRouteLoss under the same constraints
```

在金标基准中通过多路线执行建立近似 oracle；线上只在低风险任务保留 2%～5% 有界探索并记录 propensity，使用 IPS/DR 估计反事实。高风险任务不探索。

## 14. v0.5 发布门槛

以下是工程验收目标，不是当前已经取得的商业数据：

- Psuccess 整体 `ECE ≤ 0.08`、`Brier ≤ 0.18`
- 高风险分层 `ECE ≤ 0.05`
- 预测难度排序与实际失败率 `Spearman ≥ 0.70`
- 离线 normalized regret：median `≤ 8%`、p90 `≤ 20%`
- 相比全强模型基线，最终成功率非劣界不低于 `-1` 个百分点
- 高风险任务成功率不得下降
- 相比 v0.4 固定策略，CPS 改善的 95% 置信区间下界大于 15%
- 可并行任务 p95 完成时间改善至少 15%
- MultiPlanner 在困难集上扣除全部开销后成功率提升至少 5 个百分点，或 regret 下降至少 15%，才可成为默认策略
- 管理深度超过 2 的次数为 0
- Schema 合规率 100%
- 缺失依赖检测率 100%
- Handoff 引起的返工率低于 2%
- 硬预算、权限、并发和调用次数越界为 0
- deadline miss 预警 recall `≥ 90%`、AUROC `≥ 0.85`
- Provider 故障后 30 秒内熔断并切换可行路线
- 所有决策可从 EventLog 和版本快照重放

若真实数据不能达到上述门槛，应如实报告失败，不得宣传固定的“成本降至十分之一”。

## 15. 评估与发布流程

### 15.1 基线

每次 v0.5 实验至少比较：

1. 全部任务使用最强模型
2. 全部任务使用最低价模型
3. 人工静态分配
4. v0.4 规则路由
5. v0.5 自适应路由

### 15.2 基准集

- 至少 1000 个任务
- 至少 8 个任务族，每类至少 100 个
- 覆盖代码、研究、分析、决策、工具执行、长上下文、多语言、图像/视频等
- 包含“名称简单但实际高风险”的诱骗任务
- 包含本地饱和、Provider 限流、宕机、过时价格、提示注入和交接缺失
- 按时间和项目隔离数据

### 15.3 策略晋级

```text
离线回放
→ Shadow，只建议不执行
→ 5% 低风险 Canary
→ 25%
→ 50%
→ 100%
```

高风险策略在独立验证完成前不参加线上探索。

立即停止或回滚的条件：

- 成功率非劣界跌破 -1 个百分点
- 严重错误上升
- 任何硬预算或权限越界
- p95 时延恶化超过 10%
- 数据漂移或校准越过冻结门槛

## 18. 明确不做

v0.5 不做：

- 无限层级的 MetaPlanner
- 对每个简单任务强制委派
- 多模型自由辩论和无上限投票
- 仅凭模型自报置信度决定成败
- 将推理档位等同于权限
- 根据最近几条数据直接在线改写生产策略
- 高风险任务随机探索
- 未经用户启用的付费模型调用
- 把厂商宣传基准当作 CostWeave 的真实能力后验
- 在无真实对照实验时宣称固定十倍降本

## 19. v0.5 完成定义

v0.5 完成不是“页面上出现 MultiPlanner”。

只有同时满足以下条件才算完成：

1. 规划治理深度固定为两层且不可绕过。
2. 简单任务、单 Planner、多 Planner 和直接高级模型都有合理退出路径。
3. 核心路由与厂商解耦，国内外、本地和云端模型可通过统一合同注册。
4. MultiPlanner 的启用由可计算的预期收益而不是关键词决定。
5. 低价模型、强模型、本地和云端比较的是验收成功的全链路成本。
6. 并发过载和期限违约能够在执行前被预测和分流。
7. 模型交接、验证、升级和重规划都有版本化证据。
8. Outcome 数据能进入受控的校准、回放、Shadow 和 Canary 流程。
9. 新策略在成功率不劣的前提下降低 CPS，并通过置信区间和 Regret 验证。
10. 所有商业结论都能从可复现基准和真实记录中得到，而不是来自理论估算。

v0.5 的真正价值不是立即宣称超过世界顶尖系统，而是第一次让 CostWeave 具备与顶尖分流系统进行科学比较的基础：跨厂商控制、两层规划治理、全链路经济模型、实时容量感知、结构化衔接、可验证结果和可回滚学习。
