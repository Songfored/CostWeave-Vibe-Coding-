# CostWeave v0.7 重构实施路线

版本：Revision 1  
日期：2026-08-27  
上游基线：v0.6.9 Authoritative Decision Bridge  
依据：[v0.6 系列全面验收](ACCEPTANCE-v0.6-FULL.md)、[后续版本路线图](REMAINING_ROADMAP.md)

本文是 v0.7 系列的权威实施顺序。它取代 `REMAINING_ROADMAP.md` Revision 8 中原有的 v0.7.0—v0.7.5 施工细节；跨系列约束、v0.6 历史状态和 v0.8 生产门仍由 `REMAINING_ROADMAP.md` 管理。若两份文档对 v0.7 有冲突，以本文为准。

## 1. 重构结论

v0.7 不再继续增加新的 Planner、评分器或旁路页面，而是依次完成四件事：

1. 在零真实调用时把系统改造成“第一条真实数据到来就可归因、回放和生成受限修复候选”的数据就绪控制面；
2. 复用成熟 Gateway 和 Agent Runtime，只实现 CostWeave 的决策、证据和经济控制边界；
3. 先用本地快速路径处理高置信任务，只把高不确定、高风险或 OOD 任务交给深度规划；
4. 让决策权一次只迁移一个面，但不再为每个内部工作包重复发布、全量回归、完整安全扫描和页面验收。

新顺序为：

```text
v0.7.0  数据就绪主链（零付费）
   ↓
v0.7.1  真实证据桥（极小、显式授权预算）
   ↓
v0.7.2  快慢双路由与容量校准
   ↓
v0.7.3  恢复与安全策略闭环
   ↓
v0.7.4  公平竞争证明
   ↓
v0.7.5  多模态经济编排
```

版本是能力里程碑，不是每个工作包的包装单位。内部工作包使用同一开发版本和证据清单；只有达到里程碑 RC 时才更新正式版本、构建发布物并出具一次版本验收报告。

### 1.1 旧路径如何收敛

| 旧路径问题 | 重构处理 |
|---|---|
| 每个小版分别补合同、归因、回放，容易重复改底层 | v0.7.0 一次建好 Data-Ready 公共底座 |
| 先做真实调用，再补账单和 Outcome 关联 | v0.7.0 先证明模拟数据可完整归因，v0.7.1 才放行极小真实预算 |
| 多个决策模块可能一起进入主链，失败后难归因 | 工作包可并行开发，规划、路由、恢复、策略权必须串行激活 |
| 自研多个 Provider 和 Runtime，稀释项目核心价值 | Gateway/Runtime 使用 Adapter，CostWeave 聚焦经济决策控制面 |
| 每个小版机械重复全量、隔离、安全、截图和发布验收 | G0/G1 按影响增量验证，公开 RC 才做一次 G2，风险变化才做 G3 |
| 拿到真实数据后才能开始设计学习闭环 | 预置 Outcome Joiner、Attribution、Replay 和受限 Policy Patch |

## 2. 目标架构

```text
                    CostWeave Decision Plane
       Hard Constraints → Fast Router → MetaController
                │              │              │
                └──── DecisionPointRegistry ──┘
                               │
                    EvidenceEnvelopeV2
                               │
       ┌───────────────────────┴──────────────────────┐
       │                                              │
Gateway Adapter                               Runtime Adapter
LiteLLM/TensorZero/vLLM              LangGraph/MAF/OpenHands/Local
       │                                              │
       └──────── Actual Cost/Latency/Outcome ─────────┘
                               │
                         Outcome Joiner
                               │
       Attribution → Replay → Policy Patch → Shadow → Canary
```

CostWeave 不复制成熟项目的全部 Provider、限流器、分布式执行器和沙箱。它拥有任务级决策、候选召回、总成本、验收、恢复、证据归因、策略门和回滚；真实调用及运行时能力通过 Adapter 接入。

## 3. v0.7.0：Data-Ready Main Chain

### 3.1 目标

在零真实 Provider、零付费条件下，完成未来学习所需的不可变数据合同，并让“规划拓扑选择”成为第一个受控主链决策点。模型路由、Recovery 和 SafeLearning 暂不取得新的正式权力。

### 3.2 并行工作包

#### WP00-A：DecisionPointRegistry 与 EvidenceEnvelopeV2

- 注册 `planning_topology`、`candidate_recall`、`model_route`、`parallelism`、`validation_level`、`recovery_action` 和 `policy_promotion`；
- 每个决策点固定输入 Schema、动作空间、基线策略、风险级别、标签合同、探索许可和回退目标；
- 决策前冻结任务特征、候选集合、评分、选择概率、策略版本、价格和容量快照；
- 决策后只追加实际成本、延迟、验收、返工、失败类型和人工干预，不覆盖历史预测。

#### WP00-B：Outcome Joiner、候选召回和责任归因

- 把运行结果与产生它的 Decision ID 精确连接；
- 增加 Candidate Recall@K、错误淘汰原因和事后候选覆盖审计；
- 将结果归因到 Profiling、Planning、Candidate Recall、Routing、Handoff、Executor、Validator、Recovery 和 Data Quality；
- 未观察到的反事实保持 `unknown`，禁止按失败或零成本填充。

#### WP00-C：Replay 与受限 Policy Patch

- 同一冻结输入可以让 baseline 和候选策略确定性重放；
- Policy Patch 只允许调整阈值、后验、候选权重、模型隔离、升级概率、规划预算、容量估计和验收强度；
- 安全规则、权限、数据库结构、外部工具和不可逆操作不能由学习模块自动修改；
- 每个 Patch 带证据引用、作用范围、预计影响、到期时间和回滚目标。

#### WP00-D：规划拓扑受控激活

- 只允许 `NO_DELEGATION / Planner / MultiPlanner / ESCALATE` 取得主链权力；
- feature flag、策略指针、Kill Switch、baseline fallback 和结构化差分缺一不可；
- 激活失败时原 v0.6.9 baseline 继续完成；
- 同一阶段不允许模型路由、Recovery 或学习策略同时改变正式行为。

#### WP00-E：ChangeImpactManifest 与证据复用

每次变更生成：

```json
{
  "touched_decision_points": [],
  "security_surfaces": [],
  "schema_changes": [],
  "api_changes": [],
  "ui_changes": [],
  "external_call_changes": false,
  "required_gates": [],
  "reused_attestations": []
}
```

验收器根据影响清单选择测试；不再由开发者习惯性运行所有门禁。

### 3.3 v0.7.0 退出门

- 所有正式决定都有 DecisionPoint、候选集、选择概率、特征/策略版本和回退目标；
- 模拟成功与失败能精确归因并生成不具执行权的 Policy Patch；
- 规划拓扑是唯一新增权威面，其他面保持 0 干预；
- baseline 与新路径可差分、可重放、可一键回退；
- 外部调用、付费调用和训练均为 0；
- 只在 RC 执行一次 G2 里程碑验收。

## 4. v0.7.1：Real Evidence Bridge

### 4.1 目标

证明第一条真实调用可以完整进入 v0.7.0 的证据、归因和回放链。该版本只证明“数据可信且可对账”，不证明 CostWeave 已经更省钱。

### 4.2 最小范围

- 首先接一个成熟 Gateway Adapter，不并行自研多个 Provider SDK；
- 一个本地 OpenAI-compatible 端点和一个用户明确选择的外部 Provider 即可完成首轮合同验证；
- 第二个外部 Provider 只有在首个协议完全对账后才作为扩展，不阻塞 v0.7.1；
- 使用小型预注册任务集和硬验收器；
- 真实调用必须由用户显式批准总预算、模型、数据保留和停止条件；
- 数据只进入 Shadow/证据链，不自动改变路由。

### 4.3 必须对账的事实

- 请求、输入/缓存/输出 Token、重试、429/5xx、超时和 ambiguous；
- Provider 收据、内部 Cost Ledger 和最终账单；
- 请求、排队、端到端 P50/P95；
- 输出版本、独立验收、返工和人工覆盖；
- Prompt、规划、交接、验证与恢复开销；
- 无法确认的成本继续冻结，不按 0 处理。

### 4.4 立即保护与统计学习分离

单个真实事件可以触发熔断、部署隔离、预算停止、容量降级和安全回退；它不能直接修改长期能力评分。统计校准仍需达到分桶有效样本、独立标签和置信区间门槛。

### 4.5 v0.7.1 退出门

- 每条真实样本可从决策、请求、Provider 收据、账本、输出追溯到 Outcome；
- 缓存、重试和失败成本守恒；
- ambiguous 不自动重放，预算不会因为失败扩大；
- EvidenceEnvelopeV2 可以直接进入 Replay，但 Policy Patch 仍无主链权力；
- 本版执行一次 G3 专项风险验收，因为首次真实外呼触及网络、秘密、预算和副作用边界。

## 5. v0.7.2：Fast/Slow Calibrated Routing

### 5.1 目标

使用公开 E1 数据和 v0.7.1 的 E2 数据建立低开销快速路由；只有低置信、OOD、高风险或候选效用重叠时才调用 MetaController。通过门禁后，模型路由成为本版唯一新增权威面。

### 5.2 工作包

#### WP02-A：公开基准导入

- 兼容 LLMRouterBench 的 Prompt、输出、评分、Token 和成本字段；
- 公共数据标记为 E1，不冒充当前用户流量；
- 复现 Best Single、Random、静态阈值和 RouteLLM 类基线；
- 先验证候选召回，再评价排序。

#### WP02-B：本地快速路由

```text
硬约束
  → 本地语义/轻量分类器
  → 高置信直接路由
  → 低置信/OOD/高风险交给 MetaController
```

- 快速路径拥有明确 P95 开销预算；
- 不能判断时必须 `ABSTAIN/ESCALATE`；
- 不因为追求低延迟绕过权限、预算和能力硬门。

#### WP02-C：Routing Context Capsule

- 路由输入包含用户目标、当前 DAG 节点、已验收 Artifact、失败历史、剩余预算、容量和截止时间；
- 不重复发送完整会话与所有 Artifact 正文；
- Capsule 版本化、可哈希、可审计，并有 Token 上限。

#### WP02-D：校准与容量

- 按任务族、模型修订、推理档位、Provider、Endpoint 和容量分桶；
- 预测 `P(accepted)`、总成本、P50/P95、返工、升级和失败类型；
- 使用保守分层先验处理新模型；
- 本地容量消费 queue、RAM/VRAM、tokens/s、并发和 deadline；
- 模型或价格变化冻结对应候选并要求重新校准。

### 5.3 v0.7.2 退出门

- Candidate Recall、Brier、ECE、Risk-Coverage、Routing Regret、CPS 和 P95 同页报告；
- 计入判断开销后优于静态规则，或明确保持 Shadow；
- 新模型没有真实数据时不获得虚构高分；
- 只有低风险、覆盖充足的模型路由取得有界权力；
- 规划拓扑保持上一冻结策略，Recovery 和 SafeLearning 不同时激活；
- 若未触及安全边界，只执行 G2，不重复整仓安全扫描。

## 6. v0.7.3：Recovery & Safe Policy Loop

### 6.1 目标

让执行中证据改变恢复动作，并让真实成功/失败自动形成受限策略候选。该版本包含两个串行激活阶段，开发可并行，但决策权不能同时变化。

### 6.2 阶段 A：Recovery Authority

- 每个 checkpoint 更新剩余成功率、预算、关键路径、容量和污染范围；
- `continue/retry/switch/request-info/subgraph-replan/full-replan/stop` 使用同一剩余损失口径；
- 已验收且未污染的 Artifact 必须复用；
- 全量重做必须证明局部恢复不可行或风险更高；
- 阶段 A 通过并冻结为 baseline 后，阶段 B 才可开始。

### 6.3 阶段 B：Safe Policy Candidate

- Attribution Engine 自动定位 Profiling、Recall、Routing、Handoff、Execution、Validation、Recovery 或 Data Quality；
- 单次严重异常只能触发隔离、熔断和回退；
- 统计更新只生成 Policy Patch Challenger；
- Challenger 固定经过 Offline Replay → Shadow → 低风险 Canary → 晋级/回滚；
- 无独立标签、选择概率、共同支持或有效样本时自动拒绝学习。

### 6.4 v0.7.3 退出门

- Recovery Advantage 相对固定重试和全部重做为正；
- 策略候选可以追溯到 Decision、Outcome、数据版本和信用解释；
- 漂移、标签冲突、校准恶化或安全越界会冻结晋级；
- 回滚不改写历史事实；
- 执行一次 G3 专项风险验收，因为本版新增恢复权力和策略 Canary。

## 7. v0.7.4：Competitive Proof

### 7.1 三层赛场

- L1 单请求：Best Single、Cheap、Random、静态阈值、RouteLLM 类、公开 Router 与 CostWeave；
- L2 工作流：单一强模型、人工静态分工、固定 Planner、固定 MultiPlanner、成熟 Agent Runtime 基线与 CostWeave；
- L3 真实流量：只在 L1/L2 达标后按 Shadow → 1% → 5% → 20% 推进。

所有方案使用同一模型池、价格快照、任务、工具、预算、验证器和数据切分。除了单请求准确率，还必须比较拆解、候选召回、管理开销、并行、交接、验证、恢复和 Cost per Accepted Result。

### 7.2 预注册胜出线

- L1：质量非劣界 -2pp 时，相对最佳已复现非 Oracle 基线成本至少低 10%；或同成本成功率至少高 3pp；
- L2：成功率非劣时 CPS 至少低 15%，且 P95 不恶化超过 10%；或形成显著 Pareto 优势；
- 使用配对 Bootstrap 95% 置信区间；
- 胜出、失败、反例、硬件、模型、价格日期、预算和消融必须同页；
- 未达标时发布失败报告，不修改门槛。

### 7.3 验收

本版不新增运行权限时，只执行一次 G2 功能/统计验收，不重复标准安全扫描。若 L3 Canary 修改权限、预算或外部调用边界，则升级为 G3。

## 8. v0.7.5：Multimodal Economic Orchestration

保留原多模态方向，但先只实现一个最小图片或短视频场景：镜头 DAG、低成本 Probe、局部升级、缓存复用、局部重渲染和镜头级成本/验收。不同模态必须使用独立预算、数据同意和版权/人物肖像策略。

该版本触及媒体数据与新的 Provider 端点，执行一次 G3。没有 E2+ 真实数据时不宣传多模态成本优势。

## 9. 验收去重体系

减少重复验收不等于降低安全标准。新体系依据变更影响触发门禁，并复用仍然有效的证据。

### G0：持续快速门（每次变更）

- 语法、Schema、确定性、核心安全不变量；
- 受影响单元测试、属性测试和差分测试；
- ChangeImpactManifest 完整性；
- 禁止声明、外部调用默认关闭和版本事实源检查。

G0 不构建发布包、不截图、不跑整仓安全扫描。

### G1：工作包门（每个 WP 合并前）

- 受影响模块集成测试；
- 新旧路径差分、失败关闭和回滚测试；
- 对应攻击路径或权限矩阵；
- 性能/内存只测发生变化的路径；
- Schema 变化时才执行迁移和重放矩阵。

G1 产生工作包收据，不单独发布版本、不重复 README/Model Card/全量验收报告。

### G2：里程碑 RC 门（每个公开 v0.7.x 一次）

- 全量回归一次；
- 发布门禁、归档边界、SHA-256 和干净安装；
- 当前版本、README、路线图、迁移和限制一致；
- UI 只有在 Web 文件发生变化时做桌面/手机实测；
- 并发、进程、Socket、数据库或 Runtime 未变化时，不重复整套独立解释器测试。

### G3：专项风险门（按触发器，不按版本惯例）

以下任一变化触发：

- 认证、项目、地域、撤销、审批或秘密；
- 外部端点、DNS/TLS、Transport 或 Provider 响应；
- 预算结算、重试、幂等或不可逆副作用；
- 决策权迁移、Recovery 主链或策略 Canary；
- 数据保留、删除、训练资格或媒体隐私；
- 依赖/供应链、并发模型、持久化或分布式边界显著变化。

G3 包含相关威胁模型差分和原攻击路径矩阵。严格资源测试只在 Socket、流式响应、进程、并发或取消语义变化时运行；隔离测试只在 Runtime、Provider 进程或持久化边界变化时运行。只有安全边界或攻击面实质变化时才做标准整仓安全扫描；发现可报告问题、影响范围不清或高风险文件大面积变化时，才升级为深度多轮扫描。

### 9.1 证据复用条件

旧证据只有同时满足以下条件才能复用：

- 证据绑定源码范围哈希、测试版本、运行时 Schema 和策略版本；
- 对应文件、依赖、权限图、外部接口和威胁面没有变化；
- G0 安全不变量继续通过；
- ChangeImpactManifest 没有声明会使证据失效的变化。

任何一个条件不满足，就只重跑受影响证据；不能为了省时间复用失效验收。

### 9.2 触发矩阵

| 变化 | 必跑 | 可跳过 |
|---|---|---|
| 纯文档 | 链接、版本与禁止声明 | 全量、隔离、安全扫描、截图 |
| 纯 UI | UI 合同、桌面/手机、相关 API Mock | 整仓安全扫描、数据库重放 |
| 决策算法 | 属性、差分、Replay、受影响集成 | 无关 Provider/页面验收 |
| Schema/Store | 迁移、重放、兼容、并发写 | 无变化的 UI 截图 |
| Provider/外呼 | G3、安全矩阵、预算/幂等/秘密 | 无关算法全套消融 |
| 并发/Runtime | 隔离、资源、取消、租约、恢复 | 无变化的页面验收 |
| 发布候选 | G2 | 同一提交上的第二次重复 G2 |

## 10. 精简交付物

### 每个工作包只交付

1. 规格差分；
2. 数据/API 合同变化；
3. ChangeImpactManifest；
4. G0/G1 结果；
5. 已知限制和回滚方法。

### 每个公开版本只交付一次

1. Changelog；
2. 必要时的迁移说明；
3. 一份汇总验收报告；
4. 一份安全影响结论，未变化时引用仍有效的既有证明；
5. 发布物、清单和哈希；
6. 下一里程碑启动结论。

Data Card、Model Card、Policy Card、截图和完整安装说明只有内容实质变化时才更新，不再机械复制上一版。

## 11. 并行开发与串行授权

可以并行：

- 数据合同、Replay、Policy Patch 和测试选择基础设施；
- Gateway Adapter 与 Outcome Joiner；
- 公共基准导入、快速路由和容量模型；
- Recovery 算法与 Attribution Engine。

必须串行：

- 规划拓扑、模型路由、Recovery 和策略 Canary 的正式权力迁移；
- 真实 Provider 从 Shadow 到 Canary；
- 一个策略成为 baseline 后，下一策略才能开始权威实验。

这样并行开发不阻塞工程速度，同时避免多个变化同时发生导致无法归因。

## 12. 停止条件

- v0.7.0 数据合同不能把决定和 Outcome 精确连接：停止真实调用；
- v0.7.1 账单或重试无法守恒：停止扩大 Provider 和样本；
- v0.7.2 计入路由开销后不优于静态规则：保持 Shadow；
- v0.7.3 缺少独立标签、共同支持或回滚目标：拒绝晋级；
- v0.7.4 未达到预注册线：发布失败结果，不进入领先宣传；
- 任一阶段出现权限、预算、数据或副作用越界：立即回到上一冻结 baseline。

## 13. 下一步唯一动作

下一开发版本为 **v0.7.0 Data-Ready Main Chain**。首先实施 WP00-A、WP00-B 和 WP00-E；三者可并行。它们完成并通过 G1 后，再实施 WP00-C 与 WP00-D。v0.7.0 完成前保持真实 Provider、付费调用、模型路由干预、Recovery Authority 和自动策略晋级全部关闭。
