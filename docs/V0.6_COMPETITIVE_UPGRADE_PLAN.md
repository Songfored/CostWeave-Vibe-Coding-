# CostWeave v0.6 竞争性升级计划

调研日期：2026-08-09

状态：Revision 2。取代原先以“逐项补生产能力”为主的 v0.6 暂定排期。原排期保留为长期工程待办，但不再决定开发顺序。核心决策算法见 [`V0.6_DECISION_INTELLIGENCE_ARCHITECTURE.md`](V0.6_DECISION_INTELLIGENCE_ARCHITECTURE.md)。实际施工必须遵守 [`V0.6_LOW_CAPABILITY_MODEL_PLAYBOOK.md`](V0.6_LOW_CAPABILITY_MODEL_PLAYBOOK.md)；首版逐字段、逐接口、逐测试规格见 [`V0.6.0_IMPLEMENTATION_SPEC.md`](V0.6.0_IMPLEMENTATION_SPEC.md)。

## 1. 结论

CostWeave v0.5.8.4 已有较完整的离线控制面，但还不是经过真实数据证明的智能路由产品。当前最大问题不是功能数量不够，而是：

1. 88 个 Python 模块与 706 个离线测试证明了工程合同，却没有证明路由比竞品更好；
2. Provider、模型输出、账单、延迟和限流仍主要处于模拟或默认关闭状态；
3. 现有启发式规划器和路由器没有在公共路由基准上与学习型路由器公平比较；
4. 没有一个外部项目可以用相同输入、预算和验收器与 CostWeave 直接对打；
5. 产品边界过宽，容易同时与成熟网关、工作流框架、路由研究库和可观测平台竞争，结果是每一项都不够深。

因此，v0.6 的目标改为：

> 把 CostWeave 做成可插在任意模型网关和 Agent Runtime 之上的“任务级经济控制器”，并用公开、可重复的基准证明它在成本、成功率和时间的联合目标上优于已复现的强基线。

下一版确定为 **v0.6.0 Decision Intelligence Lab**。它不默认产生任何付费调用，先统一任务信念、系统信念、能力后验、完整策略、决策轨迹与公平赛场，为后续真正的元推理和联合优化建立不可绕过的入口。

## 3. CostWeave 应该选择的竞争位置

### 3.1 不与竞品正面重复的部分

- Provider 协议覆盖：交给 LiteLLM、TensorZero 或 OpenAI-compatible Gateway；
- 通用持久化 Agent Runtime：通过 Backend 接口接 LangGraph、Microsoft Agent Framework 或用户自己的运行时；
- 基础 Trace 存储与展示：输出 OpenTelemetry，不自创封闭格式；
- 提示词优化算法：允许 DSPy/GEPA 类优化器作为实验插件，不在核心中复制；
- 单请求路由研究算法：通过统一 Router 插件接入和比较，不声称每种都由 CostWeave 原创。

### 3.2 必须做深的独特部分

CostWeave 的差异化是 **Workflow-Aware Economic Orchestration**：

1. 路由单位不是一条 Prompt，而是带依赖、风险、验收标准和截止时间的任务 DAG；
2. 同时决定 `NO_DELEGATION / Planner / MultiPlanner`，管理成本也进入目标函数；
3. 同时选择模型、推理档位、并发宽度、验证强度、升级点和恢复范围；
4. 预测的是“最终通过验收的概率与总成本”，而不是模型对单题的平均分；
5. 总成本包含规划、上下文搬运、执行、验证、等待、失败、升级和返工；
6. 支持本地算力与云模型联合准入，在首次执行前识别本地拥塞；
7. 半程验收可以只重做受污染子图，也可以在证据充分时触发完整重规划；
8. 所有在线学习只能生成候选策略，必须经过离线、Shadow、Canary 和回滚门。

这使 CostWeave 有机会在“完整任务的 Cost per Accepted Result”上超过只做单请求路由或只做工作流执行的项目。

## 4. 超越竞品的可证伪标准

“超过竞品”不得由功能数量、代码行数或自评得出。必须同时建立三层赛场。

### 4.1 L1：单请求路由公平赛

数据：优先兼容 LLMRouterBench，并保留 RouterBench/RouteLLM 格式转换器。

基线至少包括：

- 最强模型全量执行；
- 最便宜模型全量执行；
- 随机路由；
- 固定难度阈值；
- RouteLLM 风格的已复现学习型基线；
- LLMRouter 中至少两个有代表性的已复现基线；
- 事后 Oracle 上界。

晋级标准：

- 在相同模型池、相同数据切分、相同价格快照和相同评分器下比较；
- 质量非劣界为 `-2` 个百分点；在此条件下，总成本至少比最佳已复现非 Oracle 基线低 10%；
- 或在相同成本下，验证成功率至少高 3 个百分点；
- 使用配对 Bootstrap 给出 95% 置信区间；置信区间未越过晋级线时才算胜出；
- 同时报告平均值、P95、失败任务族、校准误差和距离 Oracle 的 Regret。

### 4.2 L2：完整工作流赛

任务必须包含可拆分、并行、验证、返工或工具调用，不能只把单题包装成 DAG。

基线至少包括：

- 单一强模型端到端；
- 人工静态分工；
- 固定 Planner；
- 固定 MultiPlanner；
- CostWeave 自适应管理拓扑；
- 一个外部 Agent 项目输出的结构化决策轨迹，包括用户在 Claude 上完成的版本。

主指标：

- Cost per Accepted Result；
- Verified Success Rate；
- Time to Accepted Result P50/P95。

晋级标准：在成功率非劣的前提下，Cost per Accepted Result 比最佳基线低至少 15%，且 P95 时间不恶化超过 10%；或者形成统计显著的质量—成本—时间 Pareto 优势。

### 4.3 L3：受控真实流量赛

只有 L1、L2 通过后才允许进入。先 Shadow，再 1%/5%/20% Canary；任何预算越界、权限越界、显著质量下降或未知副作用都会自动回滚。

### 4.4 规划本身的硬约束

- 本地直接判定的 P95 额外延迟目标：不高于 100 ms；
- Planner 总成本占最终任务成本：中位数不高于 5%；
- MultiPlanner 仅在预期信息价值高于新增成本和延迟时启动；
- 两层管理深度是硬上限，不允许递归生成无限管理层；
- Handoff Defect Rate 目标不高于 3%；
- 预算、权限和数据驻留硬违规必须为 0；
- 所有“胜出”结论必须附数据版本、代码版本、价格快照、随机种子和置信区间。

## 5. v0.6 发布顺序（Revision 2）

新版顺序先建立统一决策状态，再逐层增加可测量的智能。核心算法与数据合同见 [`V0.6_DECISION_INTELLIGENCE_ARCHITECTURE.md`](V0.6_DECISION_INTELLIGENCE_ARCHITECTURE.md)。

### 5.1 v0.6.0：Decision Intelligence Lab（下一版）

目的：建立后续所有 Planner、Router 和学习策略必须共用的状态、动作、轨迹与公平赛场，避免再次堆出无法归因的功能。

交付：

1. `TaskBeliefV1`、`SystemBeliefV1` 与 `CapabilityPosteriorV1`；
2. `StrategyCandidateV1`：同时描述管理拓扑、分解、模型、并发、验证和恢复；
3. `DecisionTraceV2`：保存候选集、选择概率、证据、不确定性、拒绝原因和策略版本；
4. `OutcomeCreditV1`：为后续分层信用分配保留可验证字段；
5. `RoutingRecordV1` 与 LLMRouterBench、RouterBench、CostWeave 原生转换器；
6. External Trace Adapter：允许 Claude 版和其他 Agent 项目提交相同格式的决策；
7. strong-only、cheap-only、random、static、v0.5 及外部策略基线；
8. Pareto、Regret、CPS、Selective Risk-Coverage、配对 Bootstrap 和消融骨架；
9. 数据切分、价格、模型池、许可证、随机种子和声明门冻结；
10. `costweave-tournament` CLI、JSON 报告和最小对比页面。

退出门槛：默认零联网/零付费；同一输入可确定性复现；评测与生产调用同一决策入口；外部策略不得使用私有评分器；数据泄漏、价格篡改、缺失选择概率和证据不足会阻止胜出声明。

### 5.2 v0.6.1：Rational MetaController

目的：决定什么时候直接做、什么时候单 Planner、多 Planner、做低成本探针或升级专家，并把“继续思考”本身视为有成本的动作。

交付：

- Fast / Deliberate / Probe / Expert 四种路径；
- Expected Value of Computation 与 Expected Value of Information；
- 同时受金额、Token、时间和调用数约束的规划预算；
- 自适应 Planner 委员会：按边际信息与失败相关性选成员，可提前停止；
- OOD、低覆盖、高风险、资源过载和效用区间重叠时主动升级；
- 管理深度两层硬上限。

退出门槛：相对固定 Planner 和固定 MultiPlanner，规划成本中位数不高于总成本 5%，且 Decision Regret 或 CPS 有统计显著改善；没有增益时自动退回简单路径。

### 5.3 v0.6.2：Capability Evidence Graph & Calibrated Router

目的：用任务条件、模型版本、推理档位、工具、Provider 和失败相关性共同描述能力，替代静态能力分数。

交付：

- 异构 Capability Evidence Graph；
- 分层先验支持新模型冷启动；
- 成功、成本、延迟、返工与升级的条件分布；
- 模型/Validator 相关失败建模；
- 校准、Conformal 风格风险覆盖、OOD 与 `ABSTAIN/ESCALATE`；
- 价格、模型版本和任务分布漂移检测；
- Router Plugin API，与 RouteLLM、LLMRouter 类基线公平比较。

退出门槛：通过 L1 预注册晋级线，并在新模型、未见任务族和价格变化测试中保持校准；否则只作为 Shadow 候选。

### 5.4 v0.6.3：Joint Plan–Route–Schedule Search

目的：不再先分解后路由，而是联合搜索完整执行策略。

交付：

- 安全基线、历史检索、Planner 提案和局部变换组成候选工厂；
- 硬约束剪枝、Pareto 保留、Successive Halving、Beam/LUCB/Bayesian 可插拔搜索；
- 管理拓扑、DAG、模型/推理档位、工具、上下文、并发、验证和恢复联合评分；
- CVaR 尾部风险、Chance Constraints 与训练/探索成本摊销；
- 任意时刻可返回当前最佳可行策略的 Anytime 行为；
- Prompt/Handoff Compiler 的 Coverage、Contradiction、Authority 和 Information-Loss 检查。

退出门槛：在相同搜索预算下优于单节点贪心与固定模型组合；每个新增搜索器必须通过消融，不能凭算法名称进入生产。

### 5.5 v0.6.4：Execution-Time Belief Update & Economic Recovery

目的：把半程验收、资源变化和失败恢复并入同一个动态决策循环。

交付：

- Progress Belief：成功分布、关键路径、剩余预算、Artifact 验收和污染范围；
- 节点、里程碑和最终独立验证；
- `continue / retry / switch / request-info / subgraph-replan / full-replan / stop` 联合比较；
- 沉没成本排除、Artifact 复用、切换成本和剩余风险计入；
- 相关失败感知的异源 Validator；
- 动态资源/价格/期限变化触发重新决策。

退出门槛：在故障注入和真实失败样本上，CPS 优于固定重试与一律推倒重来；“察觉异常”和“采取正确行动”分别验收。

### 5.6 v0.6.5：Trace Credit Assignment & Safe Learning

目的：让真实成功与失败改进正确的组件，而不是用最终结果粗暴更新所有评分。

交付：

- Planner、Router、Handoff、Executor、Validator、Recovery 分层信用；
- 确定性定位、单节点反事实回放、分层估计和 IPS/DR 离线评估；
- 数据质量、选择偏差、延迟标签、漂移和版本治理；
- Champion/Challenger、盲测、Shadow、Canary 和自动回滚；
- Prompt、Capability、Router 和 Recovery 均只能生成候选策略；
- 无选择概率的历史数据不得伪装成无偏实验。

退出门槛：候选只在盲测和 Shadow 同时通过后晋级；训练数据、信用、策略和回滚版本完全可追溯。

### 5.7 v0.6.6：Gateway/Runtime Interop & Real Shadow

目的：在核心决策可测后接入真实世界，不自行复制成熟网关和通用 Agent Runtime。

交付：

- OpenAI-compatible、LiteLLM 和本地 Ollama/vLLM Gateway Backend；
- 流式、取消、重试、限流、缓存、账单和能力协商；
- OpenTelemetry；
- Runtime Backend 接口，可接 LangGraph、Microsoft Agent Framework 或用户运行时；
- 本地容量预测与首次执行前云端准入；
- 小预算 Shadow 实验与真实账单对账。

退出门槛：至少一个本地端点和两个 Provider 协议通过同一合同；Shadow 不干预生产；无授权仍零调用；真实成本、延迟和 Outcome 可逐项对账。

### 5.8 v0.6.7：Competitive Proof, Production & Multimodal

目的：只有核心智能已经胜出后，才完成生产扩展和图片/视频证明。

交付：

- L1 单请求、L2 完整工作流和 L3 Shadow/Canary 正式报告；
- 与用户 Claude 项目、强学习型 Router、固定 Agent 组合和单一强模型同场；
- 多租户、分布式租约、SLO/DR、GPU/Batch/Cache；
- 图片/视频 Provider、镜头级 Probe、缓存、重渲染和授权元数据；
- 失败任务族、消融、硬件、账单、价格日期和置信区间完整披露。

退出门槛：达到预注册竞争胜出线，且生产 Shadow/Canary 无预算、权限和数据越界；未通过时只发布失败报告，不得宣称世界领先。

## 6. v0.6.0 建议代码边界

```text
costweave/
├─ intelligence/
│  ├─ beliefs.py            # TaskBelief / SystemBelief
│  ├─ capability.py         # CapabilityPosterior contract
│  ├─ strategy.py           # Whole Strategy action contract
│  ├─ meta_decision.py      # fast/deliberate/probe/escalate
│  ├─ decision_trace.py     # candidates, propensity, evidence, outcome link
│  └─ credit.py             # hierarchical OutcomeCredit contract
├─ benchmark/
│  ├─ contracts.py          # RoutingRecord / DatasetManifest
│  ├─ importers.py          # LLMRouterBench / RouterBench / native
│  ├─ splits.py             # leakage-safe train/calibration/blind test
│  ├─ baselines.py          # common BaselinePlugin API
│  ├─ external.py           # Claude/third-party DecisionTrace import
│  ├─ metrics.py            # CPS/Pareto/regret/risk-coverage
│  ├─ statistics.py         # paired bootstrap and confidence intervals
│  ├─ claims.py             # evidence and claim admission
│  ├─ ablation.py           # component contribution experiments
│  └─ tournament.py         # deterministic policy tournament
└─ tournament_cli.py
```

约束：

- 复用 EventStore、Evaluation Protocol、Policy Registry 和 Release Manifest；
- 不再为每个新功能新建一套互不相通的 Store；
- Benchmark 与生产控制面必须调用同一个 Strategy 决策入口，防止“评测代码”和“线上代码”分叉；
- v0.6.0 只建立合同、基线和 Tournament，不提前伪造训练后的 Capability Posterior；
- 导入数据保持只读，原始记录和转换后记录都保存哈希；
- 可选科学计算依赖使用 extras，不破坏基础离线安装；
- `server.py` 的继续膨胀暂停，新 API 应按领域拆分 handler/service。

## 7. 与用户 Claude 项目的直接比较协议

在无法看到 Claude 项目代码和运行结果前，不能声称已经超过它。v0.6.0 将先规定一个最小互操作格式：

## 8. 明确停止做的事情

在 v0.6.0～v0.6.2 通过前，停止：

- 继续增加没有真实数据支持的启发式规则；
- 为了版本号而拆出大量微小版本；
- 自行追赶 100+ Provider 协议；
- 用模拟 AUROC、模拟降本比例或测试数量宣传智能优势；
- 把总指挥固定为本地模型或最强云模型。总指挥应是策略：低成本判定、可校准拒答、按信息价值升级；
- 无上限 MultiPlanner、递归管理层和无收益并发；
- 在没有统一赛场时依据 Demo 观感宣布超过某个项目。

## 9. v0.6 完成定义

只有满足以下条件，v0.6 才能声称“在明确范围内超过已复现竞品”：

1. 公共基准、工作流基准和评分代码可下载复现；
2. 至少一个强学习型路由基线和一个成熟 Agent 编排基线被公平复现；
3. L1 或 L2 的预注册胜出线通过，并给出 95% 置信区间；
4. 失败任务族、反例、费用、硬件、Provider、价格日期和已知偏差全部披露；
5. 真实账单与内部 CostLedger 对账；
6. Shadow/Canary 没有预算、权限或数据越界；
7. 第三方可以使用同一决策轨迹格式提交竞争结果；
8. 未通过的指标必须与通过的指标同页展示。

在这些条件之前，正确表述仍是“有竞争潜力的任务级经济控制面”，而不是“世界领先分流系统”。
